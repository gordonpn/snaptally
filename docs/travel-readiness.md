# Month-long travel readiness spike

Scope: SnapTally expense capture during approximately one month in Taipei, Hong Kong, and Vietnam. This is a repository readiness assessment for [#189](https://github.com/gordonpn/snaptally/issues/189), inspected at `b5c140d` on 2026-11-15 and synced with the converged Direction B Horizon 1 decisions in [product direction](product-direction.md). It does not certify production or target-device behavior. No real-device, roaming, storage-pressure, or timezone-switch rehearsal was performed for this spike. It is not an itinerary, booking tool, or emergency service.

## Recommendation and priorities

Use SnapTally for supported, correctly labeled expenses only after the checklist below passes on the intended phone. Native local-currency cash capture (`TWD`, `HKD`, `VND` under [#215](https://github.com/gordonpn/snaptally/issues/215)) is the highest-impact product gap. Under the converged Direction B policy, no-FX-fee credit cards abroad continue logging directly in `USD` using the immediate card-issuer amount, while foreign cash purchases will log in native currency using a cached, manually editable `fx_rate` persisted per transaction at submit time so offline intake stays 0ms. Until `#215` ships, retain local-currency cash receipts and amounts in a separate record for later reconciliation; never label `TWD`, `HKD`, or `VND` cash amounts as `USD`.

## Evidence and gaps

The intake keypad has a lower entry ceiling than the API: `maxCents` is 10,000,000, equivalent to 100,000 in the current two-decimal currencies. The API accepts up to 1,000,000 in magnitude. Native-currency validation must cover both limits, particularly for `VND`; API acceptance alone does not establish keypad entry.

The [architecture](architecture.md) describes intended capabilities as well as implemented ones. The following paths are the evidence for current behavior.

- [Intake](../src/scripts/intake-form.ts) defaults the transaction date through `getTodayDate`, stores a client UUID and `created_at`, and queues before sync. The amount keypad shifts cents and shows two decimal places. [Outbox types](../src/scripts/outbox.ts) restrict currency to `USD`/`CAD`; [API validation](../functions/api/transactions.ts) accepts only those currencies and caps absolute amount at 1,000,000. Both this ceiling and the two-decimal convention need updates for `TWD` and `VND` under `#215`. [Insertion SQL](../queries/insert_transaction.sql) stores currency but neither a captured `fx_rate` nor a `trip` tag; [monthly summary SQL](../queries/select_month_summary.sql) sums `USD` expenses only. Intake on `/` also currently provides no read-side Store Guardrail strip (`#225`). [#63](https://github.com/gordonpn/snaptally/issues/63) covers non-card `Checking` / `e-Transfer` payment rails and the ring-fenced `Property / CAD` boundary, not travel currencies. Adding a selector alone cannot deliver correct local-currency accounting.
- [Date helpers](../src/utils/date.ts) derive Today/Yesterday from local calendar components and validate calendar dates. Displayed creation times use the current device locale timezone with English formatting. An intake date is initialized in component state, so a form left open through midnight needs validation. The outbox preserves the selected `date` but does not POST client `created_at`; server creation time must not be assumed to be purchase time after offline delay. [Activity](../src/scripts/activity.ts) explicitly selects the local month with `getTodayDate().slice(0, 7)` when fetching; the API defaults to UTC only when callers omit a valid month. Validate resume and refetch behavior around month boundaries rather than assuming the Activity request uses that API fallback. `#216` covers end-to-end validation and decisions, rather than replacing the useful local helpers without evidence.
- [Outbox](../src/scripts/outbox.ts) writes IndexedDB `snaptally_db`, with localStorage fallback and an in-memory fallback when persistence is unavailable. An in-memory fallback cannot survive process termination. Inspect Sync Status and storage warnings; a save message alone is not evidence of remote persistence. The code uses Web Locks where available, with per-tab protection otherwise. Rehearse duplicate prevention across tabs and ambiguous responses; insertion uses UUID conflict handling. `401` pauses sync, `400` quarantines invalid data, and retry/backoff handles transport/server failures including `429`. Dead-letter records need explicit review, retry, or confirmed discard. Additive `fx_rate` (`#215`) and `trip` (`#224`) payload fields must hydrate legacy queued items cleanly without triggering `dead_letter_queue` quarantine while offline abroad.
- [Service worker](../public/sw.js) caches application assets and bypasses `/api/`. [Activity](../src/scripts/activity.ts) separately caches fetched data in localStorage; that cache is not a complete server backup or proof that a fresh route opens offline. Open intake and Activity online first, then validate the exact installed-PWA route sequence offline. Any Store Guardrail summary cache (`#225`) must likewise render in 0ms offline without blocking keypad taps or submission. Sync listeners use `online` and visibility changes plus timers while the page runs. There is no guarantee of background processing after the browser suspends or terminates the app.
- [Token handling](../src/scripts/intake-form.ts) uses localStorage; [API authentication](../functions/api/auth.ts) uses a bearer token. Clearing a token does not currently guarantee cache/outbox purging or prevent all in-flight repopulation, as tracked by `#191`. Retaining unsynced records and preventing silent loss is part of that existing issue. SnapTally is a single-user personal system with multi-tenancy retired per [product direction](product-direction.md); no self-service account recovery or multi-user isolation exists, and a shared bearer token must not be treated as a travel-companion account system.
- [Permissions policy](../public/_headers) disables camera, microphone, and geolocation. Current expense fields do not provide receipt attachments, coordinates, reservation addresses, or itinerary documents. Merchant text should contain only reconciliation information, not passport details, access codes, or sensitive reservation documents. Long Unicode text and locale-specific number conventions remain device-validation tasks; custom keypad input does not imply localized decimal/grouping support. Activity API search also enforces an escaped UTF-8 byte limit, which can constrain multibyte names.

## Follow-up work and owner decisions

Four Horizon 1 issues ([#215](https://github.com/gordonpn/snaptally/issues/215), [#216](https://github.com/gordonpn/snaptally/issues/216), [#224](https://github.com/gordonpn/snaptally/issues/224), and [#225](https://github.com/gordonpn/snaptally/issues/225)) address pre-departure travel readiness before December 12, 2026:

- **Currency and FX policy (`#215`, owner decisions recorded 2026-11-15):**
  - Reporting currency is `USD`.
  - No-FX-fee credit cards abroad continue logging directly in `USD` using the immediate USD amount displayed by the card issuer (no foreign card settlement queue).
  - Foreign cash purchases (`TWD`, `HKD`, `VND`) are logged per purchase in native currency so spend categories stay accurate instead of recording lump-sum ATM withdrawals.
  - Exchange rate policy uses a cached per-currency `fx_rate` refreshed asynchronously in the background when online, with manual user editability (for example, to pin a realized ATM rate). Both native amount/currency and `fx_rate` persist on each transaction at submit time so offline intake remains 0ms (no live blocking FX API lookups on submit) and the USD equivalent is deterministic.
  - `VND` and `TWD` use 0-decimal keypad entry without 2-decimal cents shifting, and the `1,000,000` numeric cap is raised appropriately for `VND`. This is an entry UX decision, not a change to currency minor units or permission to rescale stored amounts. Mixed raw currencies remain excluded from totals unless converted via persisted `fx_rate`.
- **Date and timezone boundaries (`#216`):** Before implementing fixes, confirm whether an untouched open form follows local midnight, what constitutes a purchase's calendar date when crossing zones, and whether displayed time represents capture or server insertion. Manually selected backfill and queued dates must remain stable. Validate `Asia/Taipei`, `Asia/Hong_Kong`, and `Asia/Ho_Chi_Minh`, including arrival from a different calendar day and month/year boundaries.
- **Trip tagging and Active Trip allowance (`#224`):** Add an optional nullable `trip` identifier (for example `asia-2026`) to D1, outbox payloads (backward-compatible with legacy queued items), and transaction APIs, plus an Active Trip toggle and optional USD Trip Allowance in Settings. When enabled, intake defaults `trip` to the active identifier while keeping normal category selection (`Dining`, `Bars`, `Coffee & Snacks`, `Transit`, `Travel Fund`, etc.) and allowing a manual per-entry clear so non-trip home bills logged abroad remain untagged. Pre-booked flights and hotels can use the same `trip` tag regardless of purchase date, and the API exposes trip spend summary (`spent_usd`, `allowance_usd`, `pct_used`) using persisted `fx_rate` values. Multi-trip dashboards and shared companion ledgers are out of scope.
- **Store Guardrail strip (`#225`):** Add a compact, non-blocking strip on `/` displaying top-category `% budget used` (`Guilt-Free`, `Fixed Costs`, `Savings`, excluding `Property / CAD` `#63` and `Income`), or Active Trip Allowance `% used` when Active Trip is enabled. Use one fixed primary calculation on initial view (Rolling 30-day pace so the 1st of the month does not act as a hard reset) with an explicit 1-tap toggle to Rollover balance (no silent dynamic switching), cached locally for 0ms offline render without blocking keypad taps or submission.

Use existing `#191` and `#192` for device-data cleanup and preview access, and `#63` for non-card `Checking` / `e-Transfer` rails and the `Property / CAD` boundary. Simple authenticated CSV export (`#226`) is scheduled in Horizon 2 (post-trip), and receipt splitting (`#62`) is deferred post-Horizon 2. Existing [#52](https://github.com/gordonpn/snaptally/issues/52) covers edge integration tests and [#203](https://github.com/gordonpn/snaptally/issues/203) covers consecutive submission tests. Do not expand those into unrelated travel features. If the device rehearsals below reveal persistence, rendering, or recovery failures, file a focused reproduction with browser/OS/version and queue state after checking the backlog. No failure is asserted solely from an unperformed rehearsal.

### Decisions and implementation details still to verify

The converged direction does not settle every accounting or cache contract. Keep these gaps with their existing implementation issues rather than silently choosing policies in this readiness document:

- **Native cash conversion:** Define quote direction, rounding, and missing/stale-rate behavior before claiming a deterministic USD equivalent. Cash capture must remain non-blocking offline when no usable cached rate exists. Define manual-override precedence so a background refresh cannot replace the selected realized rate before it is snapshotted on a transaction.
- **Optional trip allowance:** Define the summary and strip behavior when the allowance is absent or zero. An optional target cannot always produce a meaningful percentage; enabling a trip alone must not imply one is available.
- **Offline guardrail reconciliation:** Define how pending local expenses affect the cached signal, how acknowledged expenses avoid double counting, and how stale refresh responses are reconciled. A last-server-summary cache alone does not account for newly queued spending.
- **Home versus trip accounting:** Product direction requires trip spending to stay separate from personal daily percentages. Verify that trip-tagged entries remain excluded from personal Rolling and Rollover calculations after Active Trip is disabled, while remaining included in the trip ledger.

## During the trip

- [ ] At each entry, check date, amount, currency (`USD` for no-FX-fee credit cards; `TWD`/`HKD`/`VND` for cash once `#215` ships, otherwise separate record), `fx_rate` (adjust if pinning a realized ATM rate), `trip` tag (clear for non-trip home bills), card, and merchant against the receipt.
- [ ] Check the Store Guardrail strip (`#225`) for Active Trip Allowance `% used` as a fast non-blocking signal before purchase without delaying 0ms entry.
- [ ] After arrival or a device timezone change, check today's date and current-month summary before continuing. Preserve original dates on pending entries.
- [ ] On reliable connectivity, open the app and inspect Sync Status until pending items are confirmed remotely. Review quarantined reasons; correct/retry or explicitly discard only after preserving needed information. Re-entering a pending expense can create a new UUID and duplicate accounting.
- [ ] If access fails or a token is lost, retain pending data and use the verified recovery process. Avoid clearing browser/site storage, reinstalling, or removing the token as an improvised sync fix.
- [ ] If storage, battery, or network prevents reliable capture, switch to the independent receipt/amount record and reconcile later. Device loss cannot recover an unsynced browser-only queue from the server.

## After returning

- [ ] Flush and verify all pending and quarantined entries before cleanup; reconcile server records, independent notes, receipts, refunds, and card settlements without double entry.
- [ ] Review dates around travel boundaries and reporting periods; verify original currencies, persisted `fx_rate` conversion provenance, and `trip` tag completeness (including pre-booked flights/hotels and excluding home bills), and exclude any unsupported mixed-currency raw totals.
- [ ] Produce a verified backup/export (`#226` CSV export once available, or a verified local export) covering the trip period; omit tokens and sensitive metadata.
- [ ] Apply the agreed retention policy to receipts and local caches only after reconciliation and backup. Revoke/rotate travel access if appropriate through the verified process; token removal alone is not proof of data deletion until `#191` is resolved.
- [ ] Record failed rehearsals and actual trip friction as focused followups, including device context and sanitized evidence.
